# Design decisions and trade-offs

> This is what interviewers ask about most. Every decision must state a **reason** and a **cost**.
> To change a decision here, update this rule first and only then the code.

## Load balancer layer

- **ADR-01 — HAProxy instead of Nginx as the load balancer.** Reason: flexible active health checks, a Runtime API that enables and disables servers without a reload, a readable stats page, and it balances both HTTP and TCP so MySQL can use it too. Cost: one more technology to learn.
- **ADR-02 — Terminate TLS at HAProxy.** Reason: certificates are managed in one place and web nodes only speak plain HTTP internally, which keeps their config simple. Cost: LB to web traffic is unencrypted, acceptable inside a private network.
- **ADR-03 — Keepalived with preempt on, lb01 priority 110 and lb02 priority 100.** Reason: lb01 is always MASTER while healthy, so the state is predictable. Cost: one extra short interruption when lb01 recovers.
- **ADR-04 — Sticky cookie `SRV` on the web backend.** Reason: a user stays on one node, which makes debugging easier. Cost: not functionally required, since WooCommerce keeps sessions in the database.

## Web and application layer

- **ADR-05 — Shallow web health check: `/healthz.php` only proves Nginx reaches PHP-FPM, it never touches DB or NFS.** Reason: a health check that depends on the DB would make HAProxy mark **both** web nodes DOWN when the DB slows down, turning one failure into a full outage. Cost: it cannot detect a DB failure, not even a single-node one, so DB and NFS need their own monitoring channel.
- **ADR-12 — Code is deployed only by Ansible, with `DISALLOW_FILE_MODS=true`.** Reason: prevents the two nodes from drifting when somebody installs a plugin through wp-admin. Cost: installing a plugin becomes a process, not a button in the admin UI.
- **ADR-10 — NFS for the uploads directory instead of GlusterFS.** Reason: simple, sufficient at lab scale, easy to troubleshoot. Cost: NFS becomes a single point of failure and must be listed as a known limitation.
- **ADR-11 — Mount NFS `hard`.** Reason: upload data is not corrupted when the network is flaky. Cost: if NFS dies, processes hang in state D, which must not be mistaken for a PHP bug.

## Database layer

- **ADR-06 — The application connects to the database through `VIP:3306`, and HAProxy picks the writable node using `mysqlchk`.** Reason: web nodes do not need to know which node is primary, so changing primary is an HAProxy operation rather than a `wp-config.php` edit on every node. Cost: an extra network hop, MySQL sees the LB IP as the source address, an LB failover drops open DB connections, and because the VIP lives in the dmz zone every query crosses `fw01` twice.
- **ADR-07 — Controlled manual database failover, never automatic.** Reason: automatic failover without fencing easily produces two primaries accepting writes and corrupts order data; for money data, a few minutes waiting for a human is safer. Cost: RTO is measured in minutes and depends on the on-call person.
- **ADR-08 — Semi-synchronous replication, `AFTER_SYNC`, 3 second timeout.** Reason: the primary only reports a successful commit once the replica has received the event, so a confirmed order always exists on at least two nodes. Cost: higher write latency, and if the replica stops responding past the timeout it silently falls back to async, which makes monitoring **mandatory**.
- **ADR-09 — `super_read_only=ON` in the config file of both DB nodes.** Reason: any node that restarts comes back read-only, a simple form of fencing against two primaries. Cost: after a planned primary restart, write access must be opened by hand following runbook RB-04.

## Network layer

- **ADR-16 — Split the lab into 4 routed zones instead of one flat subnet.** Reason: dmz, app, db and client separation is what a real deployment looks like, it makes the firewall matrix meaningful, and it creates realistic routing and troubleshooting work. Cost: `fw01` is one more VM to run, every cross-zone flow needs a route plus two firewall rules, and a routing mistake now looks exactly like a firewall mistake.
- **ADR-17 — One router VM, no VRRP between routers.** Reason: a second router would double the routing complexity for a lab whose point is application HA, not network HA. Cost: `fw01` is a SPOF for every cross-zone flow, including order writes, and must be listed as a known limitation.
- **ADR-18 — Keep the VIP in the dmz zone only, with MySQL proxied through that same VIP.** Reason: one VRRP instance, one certificate, one entry point, and ADR-06 stays intact. Cost: web to DB traffic hairpins through `fw01` twice, which adds latency and puts the router in the write path. The alternative, a second VIP in the app zone, was rejected as more LB configuration than the lab needs.
- **ADR-19 — Remove the NAT NIC from lab nodes once provisioning is done, keeping it only on `fw01` and `mgmt01`.** Reason: with NAT attached, every node has a second way in and out, so the zone firewall and routing are never really tested; removing it forces all traffic onto the designed path. Cost: `vagrant ssh` and `vagrant provision` stop working on those nodes, internet access depends on `fw01` masquerade, and the removal order must be respected or a node becomes unreachable.
- **ADR-20 — Identify every NIC by a deterministic MAC address and let the provider pick the VMnet by subnet matching.** Reason: the original problem was never really the VMnet number, it was that guest interface names shift between rebuilds when Workstation reassigns PCI slots, which broke any config written against `ens33`-style names. Generating the MAC from the NIC index, the zone index and the host octet fixes that at the source: the `Vagrantfile` writes the MAC into the `.vmx`, netplan matches on `macaddress`, and the interface name becomes irrelevant. Subnet matching then lands each NIC on the right VMnet because the host VMnet layout already carries those subnets. Cost: the host VMnet layout is still a prerequisite that must exist and be correct before the first build, and if a required subnet is missing the provider will silently create a new VMnet with DHCP on rather than failing, so a stray VMnet remains possible and must be checked for by hand. The formula also carries a correctness requirement that is easy to miss: the MAC is the identity of a NIC, so it must be unique across the whole lab. The first version derived it from the third octet, which made `192.168.10.11` and `172.16.10.11` produce the same MAC and broke `mgmt01`; the zone index replaced that octet. The earlier approach of pinning `ethernetN.vnet` in the `.vmx` also worked, but it needed `allowlist_verified` to keep PCI slots stable and still left the config depending on interface names.

## Infrastructure and tooling

- **ADR-13 — All 10 VMs run Ubuntu 24.04; Rocky Linux was dropped.** Reason: a single distro family removes the per-OS branching from every Ansible role, so the effort goes into the HA design instead of into packaging differences; it also halves the boxes, repositories and service-name variations to keep straight. Cost: no RHEL-family experience in the project and no SELinux, so the AppArmor and MySQL-on-Debian-family paths have to carry that learning instead. The earlier two-family design was dropped once it became clear the branching cost more than it taught.
- **ADR-14 — Ansible owns all configuration, Vagrant owns VM lifecycle.** Reason: the lab can be rebuilt from scratch by command, which demonstrates infrastructure-as-code thinking. Cost: more time spent writing it up front.
- **ADR-15 — The control node is the `mgmt01` VM running Ubuntu 24.04, not WSL2 and not Debian.** Reason: `mgmt01` sits inside the lab network, so it does not depend on WSL2 mirrored networking, which has known problems with hypervisor host-only adapters; Ubuntu 24.04 ships Python 3.12.3, which already satisfies the 3.12 minimum that ansible-core 2.20 requires on a control node, so the whole lab can run one box and one distro. Cost: all work has to start by SSHing in from Windows, and the control node now sits only one minor version above the floor, so an ansible-core release that raises the requirement to 3.13 would force a box change rather than just a `pip` upgrade. The earlier Debian 13.7 choice bought Python 3.13 headroom, but at the price of a second distro family, a hand-built machine and a separate set of install steps to document.
- **ADR-23 — Prometheus, Alertmanager, Loki and Grafana for M8, not Zabbix and not ELK.** Reason: the deciding factor is logging, not metrics. Prometheus and Loki share one label model and one Grafana, so a metric and the log line that explains it are queried in the same place; Zabbix has no logging story, so pairing it with ELK or Graylog means two unrelated products, two UIs and far more RAM than this host has. Prometheus is also configured from files, which fits ADR-14 and the `changed=0` requirement, whereas Zabbix is configured by clicking in its web UI and is hard to make idempotent through Ansible. Cost: Zabbix is more common than Prometheus in traditional on-prem shops, SNMP and IPMI monitoring are out of reach, Prometheus has no long-term storage without Thanos or Mimir, and four components must be operated instead of one. Zabbix's model should still be understood well enough to say when it would be the better choice, since job descriptions list both.
- **ADR-22 — HAProxy 3.3 and Nginx 1.30.5 come from their upstream APT repositories, not from Ubuntu 24.04.** Reason: Ubuntu 24.04 freezes HAProxy at 2.8 and Nginx at 1.24.0, so the newer feature set and security fixes are only reachable upstream, and adding a signed third-party repository is itself a skill the Ansible roles should demonstrate. Cost: two extra repositories and signing keys to manage, upgrades no longer follow the distro release cycle, and a config written for 3.3 will not load on the 2.8 a rebuilt node would get if the repository step is skipped. MySQL 8.4 already follows the same pattern through the Oracle repository.
- **ADR-21 — `mgmt01` is both admin box and test client, and it is declared in the `Vagrantfile` like every other node.** Reason: the whole lab is then reproducible by one command, which is the point of ADR-14, and the control node stops being the one machine whose build steps live only in prose. Running load tests from the client zone still means k6 traffic takes the same routed path a real user would. Cost: `vagrant destroy` now takes the control node with it, so the SSH key pair must exist in the repo before the first `vagrant up` instead of being generated on `mgmt01`, and the control node is now coupled to the box pin and the `vagrant-vmware-desktop` plugin version. Keep a snapshot of `mgmt01` before any destructive lab operation, because losing it means losing the Vault password file and any local state that is not committed.
- **ADR-24 — `mon01` is a separate VM, not a second role on `mgmt01`.** Reason: the load generator and the measuring instrument must not share a machine. k6 competing with Prometheus and Loki for the same 2 vCPU would throttle the load source and leave gaps in the scrape data, in exactly the window being measured, which would silently corrupt every number G9 asks for. Keeping them apart also means the metric and log history lives on an Ansible-managed node rather than on the box that runs the playbooks. Cost: 2048 MB of RAM that the host does not really have spare, which is why `router02` was dropped to pay for it.
